**Field-mapping judgment calls (flagged, not silent guesses):**

1. **`blurb`** — extracted from the individual page's `<meta name="description">` via the regex `/a Stirling [^.]*\./`, e.g. `"a Stirling latte built from Syrups and Sauces."` (the description tag reads `"{Name} — a Stirling {category, lowercased/singularized} built from {lines}. {instructions...}"` — only the `"a Stirling ... ."` sentence is kept as the blurb, per the brief's literal phrasing). ## Phase 8 (verification) — two real bugs found via real-browser screenshot comparison, both fixed

This machine turned out to have a real Chrome install (`C:\Program Files\Google\Chrome\Application\chrome.exe`), discovered mid-project — every earlier phase had assumed no browser tooling existed at all. A verification agent used it to screenshot the local build against the live site and caught a real, sitewide, visually-severe bug that no source-only analysis had surfaced. Full detail in `PARITY.md`; summarized here per this file's running convention:

1. **Body background was hardcoded `plum` (dark) sitewide** in `global.css`, but the live site only uses `plum` on the homepage — every other template (flavor/recipe detail, `/recipes/`, `/spec-sheets/`, `/404/`) sets `cream` (light) via an inline `style` on `<body>`. Combined with the also-global `color: var(--ink)` (near-black), this made body text render **invisible (dark-on-dark)** on 5 of 6 page templates. Fixed by adding a `background` prop to `BaseLayout.astro` (default `plum`) and setting `background="cream"` on the 5 affected pages, matching the source's own per-page inline-style pattern exactly. The sticky dark topbar that also looked "missing" in the buggy screenshot was not a separate bug — it's a semi-transparent dark band that was blending into an equally-dark body; it appeared correctly the moment the body-background fix landed.

2. **Header logo was `/favicon.svg` (a placeholder shield icon)** instead of the real "STIRLING" wordmark — a Phase 2 scaffold leftover that no later phase happened to touch, even though the real wordmark file was already sitting in `public/images/site/` (downloaded during image localization) and already correctly wired into `Footer.astro`. Fixed by pointing `Header.astro`'s brand `<img>`/`srcset` at the same local wordmark files `Footer.astro` already used.

Both fixes verified with fresh `npm run build` + fresh headless-Chrome screenshots (not just re-reading the code) — see `reference/screenshots/*-local-fixed.png` vs `*-live.png`.

The verification agent itself was cut short by an account-level API session limit before finishing Lighthouse/axe and the real-browser motion checks — those remain genuinely un-run, not just unreported (honest gap, see `PARITY.md`).
